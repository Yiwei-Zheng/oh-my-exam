# CIE A-Level Subject Database Schema

## Scope

This document is the source of truth for CIE A-Level per-subject SQLite
databases generated by the metadata packer.

All future CIE A-Level subject databases must follow this structure unless a
new task explicitly changes this document and the packer implementation
together.

## File Naming

One subject uses one SQLite database file:

```text
{exam_board}_{qualification}_{course_code}.sqlite
```

Example:

```text
cie_a_level_9231.sqlite
```

The file itself identifies `exam_board`, `qualification`, and `course_code`, so
the database must not create separate `qualifications`, `exam_boards`, or
`courses` tables.

## Tables

Allowed core tables:

- `database_info`
- `papers`
- `questions`
- `crop_regions`
- `question_texts`

Do not create `schema_migrations`, `paper_documents`, `metadata_fields`,
`question_sources`, or FTS5 virtual/shadow tables such as
`question_fts_config` in these subject databases.

The subject database is a compact runtime index. It keeps only enough data to:

1. match OCR text against known question text;
2. identify the local QP/MS documents by their stable stems;
3. import their crop metadata into the global catalog.

## `database_info`

Stores one row for whole-database identity.

Columns:

- `id`
- `qualification`
- `exam_board`
- `course_code`
- `course_display_name`

Do not store schema/database version or timestamp fields here.

## `papers`

Stores one row per paper/component.

Columns:

- `id`
- `qp_stem`
- `ms_stem`

`qp_stem` is unique. Example:

```text
9231_w22_qp_11
```

Remote URLs are not stored. The global-catalog migration resolves these stems
against server-owned PDFs under `data/raw_papers/` and stores relative storage
keys in `paper_documents`.

## `questions`

Stores compact question identity.

Columns:

- `id`
- `paper_id`
- `local_question_key`
- `question_number`

Unique key:

```text
paper_id + local_question_key
```

Example:

```text
paper qp_stem = 9231_w22_qp_11
local_question_key = q01_b
question_number = 1(b)
```

The display/debug key can be reconstructed as:

```text
{qp_stem without "_qp_"}_{local_question_key}
```

Do not store these columns in `questions`:

- `question_key`
- `content`
- `global_question_key`
- `question_label`
- `subquestion_label`
- `parent_question_id`
- `qp_metadata_path`
- `qp_image_path`
- `ms_metadata_path`
- `ms_image_path`

## `crop_regions`

Stores one row per splitter crop segment needed to recreate the question image
from the downloaded source PDF.

Columns:

- `question_id`
- `source_type`
- `region_order`
- `page_index`
- `x0`
- `y0`
- `x1`
- `y1`
- `render_dpi`
- `join_gap_px`
- `post_left`
- `post_top`
- `post_right`
- `post_bottom`

`source_type` is compact integer-coded:

- `0`: QP
- `1`: MS

Primary key:

```text
question_id + source_type + region_order
```

`x0`, `y0`, `x1`, and `y1` are the PDF-space rectangle from splitter metadata.
`post_*` fields are nullable and are only populated when the splitter recorded
a post-render pixel crop. `render_dpi` is retained so post-render crop values
can be applied consistently.

## `question_texts`

Stores searchable QP text for OCR/search matching.

Columns:

- `question_id`
- `content`

`question_id` is the `questions.id`. `content` stores the searchable QP text
from splitter metadata and can be selected directly for debugging, snippets, or
application-side matching. MS metadata must not populate this table.
