# CIE A-Level Processed Question Layout

## Scope

Processed question output layout written by the CIE A-Level splitter.

## What belongs here

- Output directory convention.
- Image and JSON sidecar rules.
- Question filename normalization.
- Portable path rules.

## What does not belong here

- Raw PDF download workflow.
- Full `crop_regions` schema.
- Subject-specific cutter algorithms.
- SQLite schema.

## Output Layout

```text
data/processed_questions/{exam_board}/{qualification}/{subject_code}/{year}/{session}/{component}/{qp|ms}/
```

Each question output includes:

- An image file.
- A JSON sidecar.

TXT sidecars are not generated by default.

## Sidecar Fields

All CIE A-Level cutters must write the same JSON metadata schema. The current
9231 sidecar schema is the standard for all subjects, including subject-specific
cutters and the generic fallback.

QP sidecars must include exactly these stable fields:

- `question_number`: string.
- `content`: string.
- `source_stem`: string, for example `9231_w23_qp_11`.
- `document_type`: `qp`.
- `source_url`: the exact downloadable QP URL.
- `crop_regions`: list.

MS sidecars must include exactly these stable fields:

- `question_number`: string.
- `source_stem`: string, for example `9231_w23_ms_11`.
- `document_type`: `ms`.
- `source_url`: the exact downloadable MS URL.
- `crop_regions`: list.

Sidecars should not include generated output paths such as `image_paths` or `manifest_path`.
They also must not include legacy or convenience fields that are not in this
schema.

## Content Field

`content` stores the visible question stem/body text for question-paper
output. For question papers, this should be the text a student needs to
understand the sliced question, including shared stem text copied into leaf
subquestions when the image slice includes that context.

Mark-scheme sidecars must not include `content`, `content_source`, or
`content_warning`. Later structured marking data belongs in storage or
classifier outputs, not as duplicate free-text MS sidecar content.

Production cutters should populate `content` from PDF text structures first:
metadata, text spans, words, raw dict blocks, and layout order. Extracted text
must be normalized enough for search and QA, but it must not invent missing
question content.

If QP PDF text extraction is unusable because the source uses embedded font
encoding, damaged character maps, raster-only pages, or obvious mojibake, the
cutter must run OCR on the rendered question region and store the OCR result in
`content`. The sidecar or batch report should record that OCR was used so lower
confidence text can be audited later.

Extraction diagnostics belong in batch reports rather than per-question
sidecars because they are not used by the runtime database.

## Question Identity

- Leaf subquestions are the output unit.
- Examples: `1(a)`, `1(b)`, `3(a)(i)`.
- Filenames normalize question labels.

Example:

```text
9231_w23_ms_11 question 1(a) -> 9231_w23_ms_11_q01_a.json
9231_w23_qp_11 question 1(a) -> 9231_w23_qp_11_q01_a.json
```

QP and MS must use the same normalized suffix for matching question identities.
The filename must include the component before the local question key:
`{source_stem}_{local_question_key}.json`, for example
`9231_w23_qp_11_q01_a.json`. The local question key is the normalized suffix
beginning with `q`, such as `q01_a`.

## Image Format

- Grayscale JPEG at controlled quality is acceptable when formulas and fine lines remain readable.
- Black-and-white output requires visual QA.
- Correct boundaries and stable metadata matter more than a specific image format.
